## Воспроизводимая настройка учебного ресурса

1. В учебном Google-аккаунте создайте таблицу `Koleso21 — Bookings`.
2. Откройте Extensions → Apps Script. Перенесите `apps-script/Code.gs`.
3. В Project settings → Script properties добавьте `SPREADSHEET_ID` (ID только этой учебной таблицы). Токены не нужны.
4. Установите часовой пояс проекта `Europe/Moscow`, выполните `setupSheet` и выдайте разрешения учебному аккаунту. Функция не затирает данные и откажется работать при несовпадении заголовков. Листы: `leads`, `utm`, `ga4_traffic`, `ga4_leads`.
5. Deploy → New deployment → Web app. Execute as: учебный владелец, Who has access: Anyone. Скопируйте URL с окончанием `/exec`.
6. В `js/config.js` задайте публичный `window.K21_CONFIG.appsScriptUrl`. ID GA4 и URL приёмника публичны; секреты во frontend не размещают.
7. После изменения серверного кода создайте новую версию deployment. Сохранение файла само по себе не обновляет опубликованный приёмник.

## Транспорт

Frontend отправляет `fetch` POST, `Content-Type: text/plain;charset=utf-8`, JSON в теле. Это simple request без CORS preflight. Apps Script ContentService перенаправляет на `script.googleusercontent.com`; fetch следует redirect и читает JSON. Нельзя ставить `mode: no-cors`: opaque response не доказывает `ok: true`. Если доменная политика аккаунта запрещает Anyone или браузер блокирует чтение ответа, живой приём остаётся BLOCKED до корректной настройки deployment. Успех не эмулируется.

## Серверные проверки

`validatePayload` проверяет строки до 200 символов, имя 2–60, `+7` и 10 цифр, e-mail, допустимые car_type / rim_size, UUID v4, согласие, реальную будущую дату до 14 дней, московские часовые слоты 08:00–21:00, нормализованные UTM. `created_at` и `status=new` ставит сервер. Переданные клиентом status и created_at игнорируются. Формульные префиксы экранируются, телефон хранится текстом.

ScriptLock охватывает поиск дубля, проверку четырёх постов и запись. Повторный request_id возвращает `{ok:false,error:"duplicate"}` без второй строки. Занятые сервером четыре поста дают `slot_full`. Клиентский календарь использует массив учебной занятости по ТЗ и сам по себе не является синхронизированной системой бронирования; сервер дополнительно проверяет фактические строки. `no_show` освобождает пост.

В таблице порядок 13 столбцов строго как в ТЗ: request_id, created_at, name, phone, email, car_type, rim_size, slot, utm_source, utm_medium, utm_campaign, utm_content, status. utm_term сохраняется в реестре ссылок, но отсутствует в схеме leads согласно PDF. При необходимости согласуйте дополнительный столбец отдельно.

## Проверка живого приёма

- Перейдите по реальной ссылке реестра из согласованной публикации; отправьте тестовые имя и телефон.
- Сверьте request_id, московский slot и UTM в Sheets. Только после `ok:true` возникает generate_lead и переход thanks.html.
- Повторите идентичный JSON с тем же request_id: ожидается duplicate, число строк неизменно.
- Повторите с пустым/неверным телефоном: поле выдаёт ошибку, отправки нет. Прямой некорректный POST также отклоняется сервером.
- Проведите одну тестовую запись по new → confirmed → reminded → visited; вторую закройте no_show. Не объявляйте это выполненным без реальных строк и снимков.

## Доступ и данные

Таблица с персональными данными не публикуется в интернете. Viewer предоставляется конкретному учебному e-mail преподавателя. DataLens получает только необходимые обезличенные поля. Не включайте name, phone, email в GA4, URL страницы, скриншоты публичного репозитория или публичный dashboard.

Публичный endpoint учебного проекта не содержит секрета, поэтому не обеспечивает полноценную промышленную антиспам-защиту. Есть валидация, ограничение размера, lock, дедупликация, ограничение постов. Для промышленного применения потребуются дополнительные средства антибот-защиты и согласованный процесс обработки данных; в курсовой используются исключительно тестовые данные.
